# K530 QMK + Bluetooth (реверс) + OpenRGB

Проект по переводу клавиатуры **Redragon K530 Draconic** (главный чип Sonix **SN32F248B** / плата eVision **VS11K09A-1**, маркировка `4056e`; BT-модуль **PixArt PAR2801QN-GHVC**, он же PAJ2801UA-40) на кастомную прошивку **QMK (форк SonixQMK)** с сохранением/улучшением трёх вещей одновременно:

1. Полноценный RGB Matrix (per-key), в отличие от стока, где OpenRGB может только переключать пресеты.
2. Интеграция с **OpenRGB / Skydimo** (direct per-LED управление с ПК).
3. **Bluetooth** — самостоятельно реализованный (не готовый) SPI-драйвер связи с модулем PAR2801QN, восстановленный реверс-инжинирингом стоковой прошивки.

⚠️ **Статус на данный момент: RGB и базовая прошивка — рабочие и проверены на реальном железе. Bluetooth — НЕ завершён.** Транспортный уровень (SPI0, прерывания, отправка данных) подтверждённо работает, но синхронизация приёма кадров от BT-модуля ещё не решена до конца (см. раздел "Статус Bluetooth" ниже). Не считайте эту прошивку готовой к постоянному использованию по Bluetooth, пока этот раздел не будет обновлён с пометкой "решено".

Этот README написан подробно специально для того, чтобы следующий человек (или ИИ-модель), которая продолжит проект, не повторяла уже пройденные и закрытые тупиковые пути.

| Компонент | Значение |
|---|---|
| Главный MCU | Sonix **SN32F248B** (маркировка на чипе `VS11K09A-1`, `4056e`, бренд eVision), ARM Cortex-M0 |
| Bluetooth-модуль | PixArt **PAR2801QN-GHVC** (= PAJ2801UA-40, FCC ID 2AIPB-PAJ2801UA-40), BLE, отдельный Cortex-M0 |

## Bluetooth — реверс-инжиниринг протокола

Весь протокол связи между главным чипом и BT-модулем **нигде не задокументирован производителем** (проприетарно, под NDA у PixArt/EVision) и был восстановлен вручную дизассемблированием стоковой прошивки в Ghidra.

### Как был получен дамп стоковой прошивки

1. Скачан официальный Firmware Update Tool с сайта производителя (внутри архива две версии: 6-key rollover "старая" и NKRO "новая").
2. Через **Resource Hacker** извлечены встроенные в exe ресурсы `RCData`. Реальный дамп прошивки главного чипа — ресурс **`4000`** (64 КБ), остальные (`4007`–`4014`) — короткие конфигурационные строки, не код.
3. Дампы (`1RCData4000.bin` — 6-key, `2RCData4000.bin` — NKRO) импортированы в **Ghidra** (Language = ARM, Variant = Cortex, Size = 32, Endian = little, формат Raw Binary, base address = 0x0).

### Подтверждённый протокол

- Интерфейс — **SPI**, не UART (изначальная гипотеза UART была опровергнута: адреса UART0/1 не встретились в дампе; напротив, обращения к SPI0 нашлись и совпали с распиновкой).
- **SN32 = SPI slave, BT-модуль = SPI master** (модуль сам генерирует SCK и SS/CS).
- Формат кадра: **21 байт** = 20 байт данных + 1 байт чек-суммы (простая арифметическая сумма первых 20 байт по модулю 256).
- Обработчик прерывания SPI0 в стоковой прошивке — функция по адресу `0x9b2e` (найдена через таблицу векторов, адрес `0x58` = IRQ6). Полностью дизассемблирована — машина состояний: первый байт транзакции = команда, дальше 20 байт кадра пишутся в RX-буфер, одновременно в ответ идут байты из TX-буфера (какие именно — зависит от команды).
- Диспетчер исходящих команд (`0xA1`–`0xA9`), вызывается функцией `build_and_send_report`/аналог:
  - `0xA1` — обычный 6-key HID-отчёт (данные берутся из компактного 8-байтного буфера: модификаторы + 6 слотов кодов клавиш)
  - `0xA2` — команда "прочитай TX-буфер" (мастер запрашивает у слейва данные)
  - `0xA3` / `0xA4` — дополнительные типы отчётов (медиа-клавиши и т.п.)
  - `0xA7` — переключение хоста/профиля (связано со вторым физическим тумблером)
- Полная цепочка "нажатие клавиши → HID-буфер → сборка 21-байтного кадра → SPI0 → BT-модуль" была прослежена и подтверждена дословным дизассемблированием (не домыслена).

### Важные детали, найденные независимо (двойное подтверждение)

- Распиновка SPI-линий (P0.2=MISO, P0.3=MOSI, P0.4=SCK, P0.5=SS) подтверждена **дважды независимо**: через дизассемблирование стокового кода **и** через архивные обсуждения в GitHub PR `qmk/qmk_firmware#20838` и `#20839` (закрытые, не смёрженные попытки добавить BT-драйвер для K530 от сообщества).
- Физическая распиновка платы (A1–A5 для SPI, A6 для Dip Switch хоста, B13/GPIO1.13 для тумблера BT on/off) подтверждена прямыми измерениями мультиметром на реальной плате (см. раздел "Физические тумблеры").

## Текущий статус и открытые проблемы Bluetooth

### Что подтверждено рабочим (через USB-консоль на реальном железе)

- SPI0 инициализируется, прерывание подключено к правильному вектору (`Vector58`/IRQ6) — счётчик `irq_count` **растёт** при включённом тумблере BT.
- Оба физических тумблера читаются корректно (проверено логированием сырого состояния GPIO).
- Исходящие (TX) 21-байтные кадры собираются и реально уходят по SPI0 (видно в логе: `TX keyboard frame (21 bytes): A1 02 08 ...`).

### Нерешённая проблема — синхронизация приёма (RX)

При анализе сырого потока байт от BT-модуля (логирование **без** нашей собственной 21-байтной группировки) обнаружено:

- Реальный повторяющийся кусок данных от модуля: `A2 A7 00 00 00 03 FF 00 64` + ~12 нулей + `0D` — **это и есть настоящий 21-байтный кадр** (проверено вручную: `A7+03+FF+64 = 0x20D → mod 256 = 0x0D`, чек-сумма сходится идеально). То есть гипотеза "кадр = 21 байт" **верна**.
- Но между полноценными кадрами модуль передаёт дополнительные "холостые" нулевые байты (клоки идут, а логической транзакции нет), из-за чего наша программная синхронизация (`k530_receiving` — чисто софтверный счётчик "откуда считать 21 байт") **дрейфует** и часто стартует не с реальной границы кадра.
- Проверенные и отклонённые гипотезы по этому вопросу:
  - ~~SELDIS (аппаратный Auto-SEL, бит 18 CTRL0)~~ — проверено: бит уже верно выставлен (`SPI_SELDIS_EN`), включение/выключение ничего не меняет. Похоже, этот бит вообще не относится к нашей задаче — по смыслу названия ("Auto-SEL flow control") он про master-режим генерации CS, а SN32 у нас в slave-режиме, где CS — вход, управляемый внешним мастером.
  - ~~RXTOIF (RX Time-out interrupt, бит 1 RIS/IE)~~ — по датащиту порог = 32×SPIn_PCLK. Проверено на реальном железе: событие срабатывает **постоянно и всегда посреди приёма кадра**, что означает интерпретацию порога "32×HCLK напрямую" (≈0.67 мкс при 48МГц) — слишком короткий интервал, непригоден как триггер границы кадра.
  - ~~Медленный `disable()+reinit()` между кадрами~~ — измерено через `SysTick`: 0 тиков, не является причиной дрейфа.
- **Текущее направление (не завершено)**: переход от "первый байт после простоя = команда" к **скользящему окну с проверкой чек-суммы** — на каждый новый принятый байт пересчитывать чек-сумму последних 21 байт; как только сумма сходится — это гарантированная (вероятность случайного совпадения ~1/256) граница кадра, независимо от количества холостых байт до неё.

### Что делать, если продолжаете именно отсюда

1. Реализовать (или доделать) скользящее окно с чек-суммой в `k530_spi0_isr()` в `bluetooth.c` — оптимально через rolling checksum (O(1) на байт: вычитать байт, покидающий окно, прибавлять новый), а не полный пересчёт суммы на каждый байт (дорого для ISR).
2. Добавить дополнительную валидацию первого байта окна (например, что это разумное значение команды, `0xA7`/`0xA2`/т.п.), чтобы снизить шанс ложного срабатывания от случайного совпадения суммы на мусорных данных.
3. Проверить, как эта смена стратегии синхронизации влияет на уже работающий TX-путь (ответ на `cmd==0xA2`) — логика "что класть в TXBUF" должна остаться привязанной к правильному месту в новом алгоритме.
4. Команда "войти в pairing" (Fn2+ESC на стоке) **не найдена** как отдельная MCU→BT команда — рабочая гипотеза: BT-модуль отслеживает эту комбинацию автономно по обычным HID-скан-кодам, не через выделенную команду. Подтверждено эмпирически: на стоке при удержании Fn2+ESC **не передаётся никакой особый HID-код** (проверено через сайт-тестер клавиатур). Не тратьте время на поиск такой команды в дампе главного чипа — её там, скорее всего, нет.

## Физические тумблеры

На клавиатуре два тумблера: **ON/OFF** (2 положения) и **выбор хоста 1/2/3** (3 положения). Оба смысла подтверждены и физическими измерениями, и логикой в коде.

### Тумблер BT ON/OFF

- Физически подключён к **GPIO1, бит 13** (P1.13, физический вывод №47 по даташиту).
- Измерено мультиметром: положение ON → 0В на этом пине (замкнут на GND), положение OFF → пин "висит", подтягивается почти до высокого уровня резистором.
- **Важно**: сейчас в коде реализовано только **чтение** этого тумблера (прошивка узнаёт его состояние), но **нет** обратной логики "явно перевести BT-модуль в сон" при переключении в OFF. Из-за этого при подключённом USB-питании BT-модуль продолжает работать (пытается восстановить последнее соединение) даже при тумблере в OFF — это отдельная, ещё не реализованная доработка.
- Есть отдельный **силовой** тумблер батареи (отсекает батарею при отсутствии USB) — это не то же самое, что тумблер BT ON/OFF, не перепутайте их при отладке (проверено: при полностью обесточенной плате VDD падает до ~0.5В и продолжает разряжаться, это просто разряд конденсатора, ничего не говорит о логике самого BT ON/OFF тумблера).

### Тумблер выбора хоста (1/2/3)

- Подключён к двум линиям: **P0.6** (физ. вывод 23) и **P0.7** (физ. вывод 24) главного чипа.
- Физический принцип переключателя (подтверждено измерениями):
  - Позиция 1: P0.6 = 3В (питание), P0.7 = не подключён никуда.
  - Позиция 2 (среднее): P0.6 и P0.7 замкнуты друг на друга, оба "висят в воздухе".
  - Позиция 3: P0.6 = земля, P0.7 = не подключён.
- Прошивка (по найденному в дизассемблере алгоритму) кратковременно настраивает **P0.7 как выход**, выставляет на нём известное значение (HIGH/LOW по очереди), и сразу читает **P0.6** — если P0.6 "повторяет" выставленное на P0.7 значение, тумблер в положении 2 (замкнуты); если нет — читаем обычное состояние P0.6 напрямую (позиция 1 или 3).

## Сборка прошивки — окружение и грабли

### Репозиторий и ветка

База — форк **SonixQMK/qmk_firmware**, ветка **`sn32_master_openrgb`** (не `sn32_master`, не `sn32_develop` — на них у K530 либо нет нужных фич, либо версии кода разошлись настолько, что компиляция сыпется десятками несовместимых кейкодов/имён полей).

### Окружение сборки (Windows + WSL2)

QMK CLI ломается на новых версиях Python (3.12+) из-за удалённого в новых версиях модуля `ast.Num` (`AttributeError: module 'ast' has no attribute 'Num'`). Рабочее решение — **отдельное виртуальное окружение на Python 3.11**:

```bash
# в WSL2 (Ubuntu)
sudo apt install python3.11 python3.11-venv -y
python3.11 -m venv ~/qmk-env
source ~/qmk-env/bin/activate
pip install qmk

qmk setup SonixQMK/qmk_firmware -b sn32_master_openrgb
cd ~/qmk_firmware
qmk doctor   # установит недостающие arm-none-eabi-gcc и т.д., ответить Y
```

Каждый раз при новой сессии терминала перед работой — `source ~/qmk-env/bin/activate`.

### Сборка и прошивка (offset)

Для этого конкретного чипа (**SN32F248B**) официальная документация SonixQMK указывает **offset = 0x00**, **без** Jumploader (Jumploader — защитная прокладка, актуальная только для линейки SN32F26x, где выше риск "закирпичить" чип; для SN32F248B она не нужна и только всё усложняет).

```bash
qmk compile -kb redragon/k530 -km default
cp ~/qmk_firmware/redragon_k530_default.bin /mnt/c/Users/<you>/Desktop/
```

Прошивка — через **Sonix Flasher / Sonix Keyboard Flasher** с offset **0x00**.

### Частые ошибки компиляции и их решения

- **`AttributeError: module 'ast' has no attribute 'Num'`** — используете системный Python вместо venv на 3.11 (см. выше).
- **`There are not enough available endpoints to support all functions...`** — слишком много USB-функций одновременно (Mouse Keys + Extra Keys + Console + NKRO + и т.д. упираются в лимит эндпоинтов чипа). Решение — отключить лишнее в `rules.mk` (`MOUSEKEY_ENABLE = no`, `EXTRAKEY_ENABLE = no`, при необходимости временно `NKRO_ENABLE = no` на время отладки BT через консоль) или временно `OPENRGB_ENABLE = no` (он тоже добавляет отдельный Raw HID эндпоинт).
- **`'RGB_MATRIX_CYCLE_LEFT_RIGHT' undeclared`** — если временно выключаете `OPENRGB_ENABLE`, включается запасной (fallback) стартовый режим RGB, которого может не быть в списке включённых эффектов. Явно задайте `#define RGB_MATRIX_STARTUP_MODE RGB_MATRIX_SOLID_COLOR` в `config.h`.
- **`bootloader: 'sn32-dfu' is not one of [...]`** — расхождение версий схемы `info.json`/`keyboard.json` между ветками. На `sn32_master_openrgb` (этот репозиторий) актуальное значение — `sn32-dfu`, менять не нужно; это всплывало только при экспериментах с другими ветками/датированными коммитами.
- **`OPENRGB_ENABLE` и `VIA_ENABLE` нельзя включить одновременно** — это жёсткая проверка на этапе сборки (`common_features.mk`), а не баг. Протоколы используют один и тот же Raw HID канал и физически конфликтуют. Выбирайте что-то одно.
- **Мерцание индикаторов/подсветки поверх RGB-эффекта** — если пишете свою LED-индикацию (`rgb_matrix_indicators_user`), на медленном MCU может быть гонка между батчевой отрисовкой базового эффекта и вашим кодом. Решение: использовать `rgb_matrix_indicators_advanced_user(led_min, led_max)` вместо простой версии, и/или в `config.h` задать `#define RGB_MATRIX_LED_PROCESS_LIMIT 63` и `#define RGB_MATRIX_LED_FLUSH_LIMIT` побольше (вплоть до значения ≥ количества LED, чтобы убрать батчинг совсем — для 63 LED это не создаёт заметной нагрузки).
- **Розовый оттенок вместо белого при 255/255/255** — обычная особенность дешёвых RGB-светодиодов (разная физическая яркость каналов). Единая настройка коррекции в QMK отсутствует; в этом проекте используется подобранное вручную соотношение **R150/G255/B100** вместо чистого `RGB_WHITE` во всех местах, где нужен визуально белый цвет.

## Прошивка (flashing) и восстановление

### Обычная прошивка

Используйте **Sonix Flasher** (community-инструмент) или официальный EVision Firmware Update Tool (для стоковой прошивки). Offset = **0x00** для этого чипа.

### Как восстановить клавиатуру, если что-то пошло не так ("кирпич")

1. Проще всего: кейкод **`RESET`** в раскладке (у нас назначен на правый Ctrl в слое Fn1) — программно переводит в bootloader, пока прошивка вообще способна выполняться.
2. Если прошивка совсем не запускается: **аппаратное восстановление** — физически замкнуть **ножку №3** чипа (`BOOT`, `P2.2`) на GND в момент подачи питания:
   - Полностью обесточить клавиатуру (USB отключён), подождать 30-60 секунд.
   - Найти ножку 3 на корпусе главного чипа (от маленькой круглой метки на углу корпуса отсчитать против часовой стрелки: 1, 2, **3**).
   - Замкнуть её на GND (USB-экран/минус батарейного контакта) тонкой проволочкой/пинцетом, удерживая контакт.
   - Не отпуская замыкание, подключить USB.
   - Подождать 1-2 сек после подключения, затем можно отпустить.
3. Всегда держите под рукой оригинальный дамп стоковой прошивки (`1RCData4000.bin` / `2RCData4000.bin`, извлечены через Resource Hacker из официального Firmware Update Tool) — на случай, если нужно вернуться к полностью стоковому поведению.

## RGB Matrix, OpenRGB и Skydimo

### Как включена интеграция

В `rules.mk`: `RGB_MATRIX_ENABLE = yes`, `RGB_MATRIX_DRIVER = SN32F24xB`, `OPENRGB_ENABLE = yes` (в текущем состоянии репозитория временно `no` — включён режим отладки Bluetooth через консоль, см. предупреждение в начале файла `rules.mk`; для повседневного использования верните `OPENRGB_ENABLE = yes` и `CONSOLE_ENABLE = no`).

`OPENRGB_ENABLE` реализует встроенный в QMK протокол "QMK OpenRGB" (raw HID, interface 1, usage page `0xFF60`, usage `0x61`) — это стандартный, давно существующий протокол, а не что-то самописное.

### Настоящий OpenRGB (программа)

Устройство **не появляется автоматически**. Нужно вручную зарегистрировать: **Settings → OpenRGB QMK Protocol → Add**, указать VID `0x0C45` и PID `0x5004`, **Save**, затем **полностью перезапустить** OpenRGB (не просто свернуть — список детекторов регистрируется один раз при старте программы) и только потом нажать Rescan.

### Skydimo (сторонний, платный аналог)

Skydimo НЕ является простой обёрткой над OpenRGB — у него собственная система плагинов на **Lua** (`manifest.json` + `main.lua`), которую пришлось написать с нуля, реализуя тот же HID-протокол вручную:

- Плагины кладутся в `%APPDATA%\com.skydimo.desktop\plugins\dev\<имя_папки>\`.
- `manifest.json` должен содержать точный `interface_number` — подтверждено через **USB Device Tree Viewer**: **Interface 1** (Vendor-Specific, Usage Page `0xFF60`, Usage `0x61`), длина отчёта — **65 байт** (1 байт Report ID + 64 байта данных QMK-протокола).
- Структура `main.lua` должна следовать паттерну: `local plugin = {}`, функции `plugin.on_validate()`, `plugin.on_init()`, `plugin.on_tick(dt)`, `plugin.on_shutdown()` **без параметра `device`** в сигнатуре (он берётся из глобальной переменной окружения, которую инжектирует сам загрузчик Skydimo) — и `return plugin` в конце файла. Это выяснено сравнением с реально рабочим сторонним плагином (`controller.frenzy_keyboard`), а не из официальной документации (в ней это не описано явно).
- Один output-объект (`add_output` с `type="matrix"`, `size=63`) с **одним и тем же строковым id**, используемым и при регистрации, и при последующих запросах цвета (`get_rgb_bytes(id)`/`output_led_count(id)`) — рассинхронизация id между `add_output()` и остальным кодом была одной из причин, почему подсветка не включалась при формально "найденном" устройстве.
- После добавления плагина и настройки VID/PID — **обязательно полный перезапуск** Skydimo перед проверкой в разделе OpenRGB Bridge.

Готовый плагин для Skydimo лежит в этом репозитории (см. структуру ниже) как рабочий пример.

## Кастомная раскладка (keymap.c)

Слои: `_BASE`, `_FN` (обычный Fn — F1-F12, навигация), `_FN_CAPS` (удержание CapsLock = "Magic Fn", то же что `_FN`, но с макросами на цифрах 1-6), `_FN2` (второй физический Fn, ESC оставлен как заглушка — на стоке эта комбинация не передаёт HID-код вообще, поведение специально повторено), `_FN2_REC` (вложенный слой: удержание Fn2 + "7" — выбор слота записи макроса).

### Макросы

Собственный (не встроенный QMK Dynamic Macro) движок с честной **отменой без сохранения** и статусом "слот записан/пуст" для LED-индикации — то, чего нет у стандартного `DM_RSTP` (он сохраняет, а не отменяет запись). 6 слотов, запись/воспроизведение назначены на цифровой ряд под Fn2+7 (выбор слота) и Magic Fn соответственно.

### LED-индикация

- Разный цвет подсветки клавиш активного слоя (Fn1/Fn2/Magic Fn).
- Статус слотов макросов (зелёный = записан, красный = пуст) при удержании Magic Fn или Fn2+7.
- Клавиша `RESET` (сброс в bootloader) всегда подсвечена красным независимо от цвета слоя — чтобы визуально не перепутать с обычной функциональной клавишей.
- Реактивная подсветка при нажатии любой клавиши: держится на полной яркости пока клавиша зажата, после отпускания — плавное (квадратичное) затухание до базового цвета фона, а не резко в чёрный.
- Все LED-эффекты реализованы через `rgb_matrix_indicators_advanced_user(led_min, led_max)` (не простую версию без параметров) — важно для отсутствия мерцания на медленном MCU.

- ~~`FUN_000039b8`/`FUN_00003618` (GPIO P0.1 set/clear)~~ — это простой строб/enable сигнал, не побитовая SPI-передача данных.
- ~~`FUN_00008fc8`~~ — оказалась функцией записи во флеш-память, не имеет отношения к BT-протоколу.

- ~~SELDIS (Auto-SEL, бит 18 CTRL0)~~ — не относится к синхронизации кадра в slave-режиме (см. раздел про статус Bluetooth).
- ~~RXTOIF как триггер границы кадра~~ — порог тайм-аута слишком короткий (~0.67 мкс), ложно срабатывает посреди кадра.
- ~~Медленный `disable()+reinit()` между кадрами~~ — измерено: 0 тиков SysTick, не является причиной проблем синхронизации.

- ~~Ветки `sn32_develop`, `sn32_master` (обычная, без orgb) для K530 с VIA~~ — не содержат актуальной для текущей версии QMK конфигурации K530 (либо платы нет вовсе, либо десятки несовместимых по именам кейкодов/схеме `info.json` ошибок). Рабочая база — именно `sn32_master_openrgb`.
- ~~`VIA_ENABLE` вместе с `OPENRGB_ENABLE`~~ — несовместимы принципиально (см. `common_features.mk`), не пытайтесь включить оба.
- ~~Смена VID/PID устройства как способ заставить OpenRGB его увидеть~~ — не помогает (проверено на паре разных VID/PID), настоящая причина была в том, что после добавления устройства вручную в Settings нужен полный перезапуск программы, а не Rescan.

## Как продолжить работу над Bluetooth

1. Реализовать скользящее окно с rolling checksum для определения границы 21-байтного RX-кадра (см. раздел "Текущий статус и открытые проблемы").
2. После стабильной синхронизации кадра — проверить, действительно ли реальные нажатия клавиш (не только heartbeat/статусные пакеты `0xA7`) долетают до подключённого по Bluetooth хоста.
3. Реализовать логику явного перевода BT-модуля в сон при тумблере в положении OFF (сейчас реализовано только чтение состояния тумблера, обратной команды в сторону BT-модуля нет).
4. Если появится доступ к логическому анализатору — можно окончательно снять реальный SPI-трафик и сверить с восстановленным протоколом напрямую, а не только через диагностику встроенным логированием.
5. Опционально: разобраться с логикой переключения хоста (связь тумблера 1/2/3 и команды `0xA7`) — физически тумблер читается, но привязка к отправке команды переключения хоста в текущем коде ещё не реализована/не проверена.

## Дисклеймер / безопасность

- Это результат самостоятельного реверс-инжиниринга закрытого протокола, официально нигде не задокументированного. Используйте на свой риск.
- Перед экспериментами держите под рукой дамп оригинальной стоковой прошивки и знайте расположение аппаратного BOOT-пина (нога №3) — это единственный гарантированный способ восстановления, если что-то пойдёт не так на уровне, когда даже кейкод `RESET` в раскладке недоступен (например, экспериментальный код Bluetooth подвесит основной цикл).
- Bluetooth-часть прошивки — экспериментальная и незавершённая (см. статус выше). Не используйте эту прошивку как единственную на важной/рабочей клавиатуре, пока раздел статуса не будет обновлён.
