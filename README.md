# K530 QMK + Bluetooth (реверс-инжиниринг) + OpenRGB

Кастомная прошивка QMK для клавиатуры **Redragon K530 Draconic** (главный чип Sonix **SN32F248B** / плата eVision **VS11K09A-1**; BT-модуль **PixArt PAR2801QN-GHVC**), собранная на основе форка [SonixQMK/qmk_firmware](https://github.com/SonixQMK/qmk_firmware), ветка `sn32_master_openrgb`.

> **Статус: экспериментальный проект, работа не закончена.** Прошивайте на свой риск. Обязательно сохраните бэкап стоковой прошивки и заранее убедитесь, что знаете способ восстановления (см. раздел «Bootloader / восстановление» ниже), прежде чем экспериментировать.

## Цели проекта

1. **Полноценный per-key RGB через OpenRGB / Skydimo** (direct mode), вместо ограниченного стокового RGB (только переключение пресетов).
2. **Кастомный keymap**: Fn / Fn2 слои, Magic Fn (удержание Caps Lock), 6 слотов записи макросов с LED-индикацией, реактивная per-key подсветка.
3. **Реверс-инжиниринг Bluetooth** — чтобы клавиатура могла работать по BLE на кастомной QMK-прошивке (существующие альтернативные прошивки сообщества полностью убирают поддержку BT).

## Железо

- Главный MCU: Sonix SN32F248B (маркировка на чипе `VS11K09A-1`)
- BT-модуль: PixArt PAR2801QN-GHVC (BLE, отдельный Cortex-M0), связь с главным чипом — SPI (SN32 в роли slave)
- 2 физических тумблера: BT on/off (GPIO1.13) и выбор хоста 1/2/3 (GPIO0.6 + GPIO0.7)

## Сборка прошивки

```bash
# через QMK CLI (нужен Python 3.11, см. примечание про баг ast.Num на 3.12+)
qmk setup SonixQMK/qmk_firmware -b sn32_master_openrgb   # или клонировать этот репозиторий напрямую
# скопировать содержимое keyboards/redragon/k530 из этого репозитория поверх
qmk compile -kb redragon/k530 -km default
```

Флашинг: используйте [Sonix Flasher](https://github.com/SonixQMK/sonix-flasher) или официальный EVision-инструмент из `Redragon_K530_Keyboard/`, offset `0x00` (Jumploader для этого чипа не требуется — только для SN32F26x, см. официальную документацию SonixQMK).

```bash
sudo add-apt-repository ppa:deadsnakes/ppa -y && sudo apt update
sudo apt install python3.11 python3.11-venv -y
python3.11 -m venv ~/qmk-env && source ~/qmk-env/bin/activate

```

### Если включена консоль для отладки (`CONSOLE_ENABLE=yes`)

Учитывайте лимит USB endpoint'ов чипа: одновременно Console + NKRO + Extra Keys + OpenRGB (Raw HID) может не поместиться ("There are not enough available endpoints..."). Временно отключайте NKRO/Extra Keys/OpenRGB на время отладки Bluetooth, возвращайте после.

## Bootloader / восстановление

- **Программно (штатно, пока прошивка жива):** кейкод `RESET` в раскладке (в этом keymap — Fn1 + правый Ctrl).
- **Аппаратно (работает всегда, независимо от состояния прошивки):** разобрать клавиатуру, найти вывод №3 чипа (маленькая метка-точка на корпусе — от неё отсчитать против часовой стрелки: 1, 2, 3), замкнуть его на GND в момент подачи питания (подключения USB). Подождать ~30-60 сек после отключения питания перед этим, чтобы конденсаторы разрядились.
- Sonix Flasher / Jumploader для чипа SN32F248B не требуется.

## RGB Matrix, OpenRGB и Skydimo

### Цветокоррекция сделана в ядре QMK, не в keymap.c

На реальных светодиодах этой клавиатуры чистый белый (255,255,255) выглядит розовым (физический дисбаланс яркости каналов). Коррекция сделана один раз, глобально, прямо в `quantum/rgb_matrix/rgb_matrix.c`, в функции `rgb_matrix_set_color()`:

```c
void rgb_matrix_set_color(int index, uint8_t red, uint8_t green, uint8_t blue) {
    red   = (uint16_t)red   * 127 / 255;
    green = (uint16_t)green * 255 / 255;
    blue  = (uint16_t)blue  * 127 / 255;
    rgb_matrix_driver.set_color(index, red, green, blue);
}
```

Это значит: любой код, который где-либо вызывает `rgb_matrix_set_color()` (встроенные анимации QMK, direct-режим OpenRGB, кастомные индикаторы в keymap.c), автоматически получает верную цветокоррекцию на выходе. В `keymap.c` **не нужно** подставлять скорректированные R/G/B вручную — используются обычные `RGB_WHITE`, `RGB_RED` и т.д. Если переносите это на другую ревизию платы/партию светодиодов — коэффициенты могут потребовать подбора заново.

### OpenRGB (программа)

Устройство не появляется автоматически. Порядок действий (важно соблюдать именно так):

1. **Settings → OpenRGB QMK Protocol → Add**, указать VID `0x0C45` и PID `0x5004`, **Save**.
2. **Полностью перезапустить OpenRGB** (не просто Rescan — детекторы динамических HID-устройств регистрируются один раз при старте программы; без полного перезапуска новое устройство не появится, сколько раз ни нажимай Rescan).
3. Только после перезапуска — Rescan.

### Skydimo (плагин в этом репозитории)

Skydimo использует собственную систему плагинов на Lua (не связан напрямую с оригинальным приложением OpenRGB). Готовый рабочий плагин — папка `controller.k530/` в этом репозитории.

**Установка:** скопируйте папку `controller.k530` в `%APPDATA%\com.skydimo.desktop\plugins\dev\`, добавьте плагин через интерфейс Skydimo (выбор папки на диске), **обязательно полностью перезапустите Skydimo** (та же причина, что и для OpenRGB выше).

Ключевые технические детали протокола:
- Interface number для HID-правила в `manifest.json` — **1** (подтверждено через USB Tree View: Interface 1, Vendor-Specific, Usage Page `0xFF60`, Usage `0x61`, 65-байтный отчёт = 1 байт Report ID + 64 байта данных QMK-протокола).
- Структура `main.lua`: `local plugin = {}`, функции `plugin.on_validate()`, `plugin.on_init()`, `plugin.on_tick(dt)`, `plugin.on_shutdown()`, и `return plugin` в конце — модуль-таблица, а не глобальные функции.
- `device` в этой архитектуре — глобальная переменная окружения, инжектируемая загрузчиком Skydimo, а не параметр функций жизненного цикла.
- Получение текущих цветов для отправки: `device:output_led_count(output_id)` + `device:get_rgb_bytes(output_id)`.
- `output_id` — строка (в этом плагине `"leds"`), заданная один раз в `add_output()` и используемая тем же значением везде далее.

### VIA и OpenRGB несовместимы одновременно

В этой версии QMK (`common_features.mk` явно запрещает включать оба флага разом — общий Raw HID endpoint конфликтует). В этом репозитории выбран OpenRGB, без VIA.

## Кастомная раскладка (keymap.c)

Слои: `_BASE`, `_FN` (обычный Fn — F1-F12, навигация, стрелки, Home/End/PgUp/PgDn), `_FN_CAPS` (удержание CapsLock = «Magic Fn»: та же навигация, что и в `_FN`, но цифровой ряд 1-6 воспроизводит макросы вместо F1-F6), `_FN2` (второй физический Fn, назначен на клавишу в правом нижнем углу через `LT(_FN2, KC_APP)` — короткое нажатие даёт ContextMenu, удержание переключает слой), `_FN2_REC` (вложенный слой: удержание Fn2 + клавиша выбора слота записи, позиция "7" в раскладке — выбор слота для записи макроса, как на стоке).

### Тайминги

Удержание CapsLock (Magic Fn) и Fn2 (оба через `LT()`) — **300 мс** (`get_tapping_term`), подобрано опытным путём для комфортного использования (не как в стоке, где было 2000 мс).

### Макросы (6 слотов)

Собственный движок (не встроенный QMK Dynamic Macro) с честной **отменой без сохранения** и статусом «слот записан/пуст» для LED-индикации — то, чего нет у стандартного `DM_RSTP` (он сохраняет, а не отменяет запись). **6 слотов** (`macro_buf[6]`), запись/выбор слота — удержание Fn2 + клавиша выбора слота → цифра 1-6 (`REC1_TOGGLE`...`REC6_TOGGLE`); воспроизведение — удержание Magic Fn (CapsLock) → цифра 1-6 (`MACRO_PLAY1`...`MACRO_PLAY6`). Повторное нажатие той же клавиши во время записи — сохранение; удержание Fn2+выбор без нажатия цифры и последующее отпускание — отмена записи без сохранения.

Воспроизведение макроса идёт в обход обычного `process_record_user` (через `register_code16`/`unregister_code16`), поэтому Bluetooth-трекер синхронизируется отдельным явным вызовом `bt_track_basic_keycode()` внутри цикла воспроизведения — иначе воспроизведённые макросом клавиши не долетали бы до BT-хоста.

### LED-индикация

- Разный цвет подсветки клавиш активного слоя: Magic Fn — оранжевый, Fn2 — красный, Fn1 — зелёный.
- Клавиша `RESET` (сброс в bootloader) — всегда подсвечена красным независимо от цвета слоя.
- Клавиша `RGB_TOG` (MR/Backspace) — всегда подсвечена фиолетовым независимо от цвета слоя.
- Статус слотов макросов (зелёный = записан, красный = пуст) при удержании Magic Fn или Fn2+выбор слота.
- Реактивная подсветка при нажатии любой клавиши: держится на полной яркости (белый) пока клавиша зажата, после отпускания — плавное квадратичное затухание до базового тёмно-серого фона (не резко в чёрный), длительность 800мс.
- Реализовано через `rgb_matrix_indicators_advanced_user(led_min, led_max)` (не простую версию) — важно для отсутствия мерцания на медленном MCU (см. раздел «Сборка прошивки — грабли»).

### Bluetooth-интеграция в keymap.c

Параллельно основному QMK HID-отчёту (который при `NKRO_ENABLE=yes` может переключаться в NKRO-формат) в `keymap.c` ведётся **независимый компактный 6-key трекер** (`bt_report_mods`/`bt_report_keys[6]`), обновляемый на каждое базовое нажатие/отпускание через `bt_track_basic_keycode()`. Именно из этого трекера собирается кадр для отправки через `bluetooth_send_keyboard()` (в `bluetooth.c`) — независимо от того, что творится с USB HID-отчётом. Составные keycode (`LT()`/`MO()`/кастомные коды > 0xFF) явно исключены из трекера — иначе сама активация слоя (не настоящее нажатие клавиши) попадала бы в BT HID-отчёт как «нажатая клавиша».

## Bluetooth — реверс-инжиниринг протокола

Протокол связи между главным чипом и BT-модулем нигде не задокументирован производителем (проприетарно) и восстановлен вручную дизассемблированием стоковой прошивки в Ghidra (дампы `1RCData4000.bin`/`2RCData4000.bin` в `Redragon_K530_Keyboard/`, извлечены через Resource Hacker из официального Firmware Update Tool).

### Подтверждённый протокол

- Интерфейс — **SPI** (SN32 = SPI0 **slave**, BT-модуль = **master**). Линии: P0.2=MISO0, P0.3=MOSI0, P0.4=SCK0, P0.5=SEL0/SS (подтверждено дважды: дизассемблированием и архивными PR qmk/qmk_firmware #20838/#20839).
- Регистры SPI0 — база `0x4001C000` (CTRL0, CTRL1, CLKDIV, STAT, IE, RIS/IC на `+0x18`, DATA на `+0x1C`), подтверждено официальным SVD (SN32F240B) и дизассемблером.
- Вектор прерывания SPI0: адрес `0x58` в таблице векторов = IRQ6 (`SN32_SPI0_HANDLER = Vector58`, `SN32_SPI0_NUMBER = SPI0_IRQn` в `sn32_registry.h`).
- **Формат кадра:** 21 байт = 20 байт данных + 1 байт чек-суммы (сумма первых 20 байт по модулю 256). Подтверждено дважды (TX и RX сторона) и подтверждено вручную посчитанной чек-суммой на реальном перехваченном трафике: `A7 00 00 00 03 FF 00 64` — сумма первых 20 байт совпадает с последним байтом `0x0D`.
- Диспетчер исходящих отчётов (стоковая прошивка): команды `0xA1` (6-key HID), `0xA2` (запрос TX-буфера/чтение), `0xA3`/`0xA4` (медиа/др.), диапазон `0xA1-0xA9`. Командный байт `0xA7` подтверждён как переключение хоста/профиля.
- Физические тумблеры: **BT on/off** — GPIO1 бит 13 (P1.13), подтверждено измерением мультиметром (0 = ON, HIGH = OFF). **Выбор хоста 1/2/3** — GPIO0.6 + GPIO0.7, слайдер с общим контактом: в позициях 1/3 один из пинов замкнут на GND/питание, в средней позиции оба пина замкнуты друг на друга (floating). Прошивка кратковременно переключает P0.7 в режим выхода и смотрит реакцию P0.6, чтобы различить все 3 положения.

### Известные тупиковые гипотезы (не тратьте время на них снова)

1. **SELDIS (Auto-SEL, бит 18 CTRL0)** — рассматривался как способ аппаратно привязать начало SPI-транзакции к линии SEL0/CS. Оказался нерелевантным: этот бит описывает поведение периферии в роли SPI **master**, а наш чип работает в **slave**-режиме, где линия CS — вход, управляемый внешним мастером. Бит уже правильно выставлен (Auto-SEL EN) во всех тестах, дрейф синхронизации сохранялся независимо от этого бита.
2. **RXTOIF (RX time-out interrupt, RIS/IE/IC бит 1, порог 32×SPIn_PCLK по даташиту Sonix)** — рассматривался как альтернативный триггер границы кадра вместо программного счётчика байт. Эмпирически исключён: на реальном железе флаг срабатывает практически непрерывно и всегда «посреди» уже идущего приёма (порог оказался слишком коротким — вероятно это 32×HCLK напрямую, ≈0.67 мкс при 48МГц, а не 32×делённой через CLKDIV частоты). Использовать этот флаг как границу кадра нельзя.
3. **CPHA/CPOL (полярность/фаза SPI)** — проверено числами из `SPI.h`: `SPI_CPHA_FALLING_EDGE=0`, `SPI_CPOL_SCK_IDLE_LOW=0`, `SPI_MLSB_MSB=0`. Безусловная запись `CTRL1=0` в стоковой прошивке точно совпадает с этими «стандартными» значениями — это не источник проблемы.
4. **Задержка `disable()+reinit()` между кадрами** — измерена через `SysTick->VAL` на реальном железе: **0 тиков**, то есть не является узким местом.

### Открытый вопрос (на момент этого README)

Анализ сырого потока байт (без интерпретации через 21-байтную рамку) на реальном железе показал воспроизводимый паттерн: `A7 00 00 00 03 FF 00 64` + ~12-17 «холостых» нулевых байт + `0D` + затем одиночный байт `A2` (запрос) — то есть 21-байтный кадр подтверждён чек-суммой (`A7+03+FF+64 mod 256 = 0x0D`, сходится), но между логическими сообщениями от BT-модуля идут «холостые» клоки/байты, которые текущая реализация (программный счётчик `!k530_receiving`, сбрасываемый только после ровно 21 принятого байта) не умеет корректно пропускать — отсюда дрейф позиции кадра при разборе вручную. **Наиболее многообещающее направление на данный момент:** синхронизация через скользящее окно на 21 байт с проверкой чек-суммы на каждый новый принятый байт (rolling checksum), вместо жёсткой границы «раз в 21 байт», — считать кадр найденным только когда контрольная сумма скользящего окна сошлась. Это не зависит от количества и происхождения холостых байт между сообщениями.

## Физические тумблеры — как читаются в прошивке

```c
// GPIO1 бит 13 — BT on/off
// 0 = ВКЛЮЧЕН (тумблер замкнут на GND)
// 1 = ВЫКЛЮЧЕН

// GPIO0 бит 6 (P0.6) и бит 7 (P0.7) — слот хоста
// Позиция 1: P0.6=HIGH, P0.7 floating
// Позиция 2 (средняя): P0.6 и P0.7 замкнуты друг на друга
// Позиция 3: P0.6=GND, P0.7 floating
// Прошивка кратковременно настраивает P0.7 как выход и проверяет реакцию P0.6
```

## Как продолжить работу

1. **Главный приоритет** — решить синхронизацию границы RX-кадра в Bluetooth-протоколе (см. раздел выше). План: rolling checksum по скользящему 21-байтному окну вместо жёсткого счётчика.
2. После стабильного приёма — протестировать полный цикл: нажатие клавиши → передача по SPI → приём BT-модулем → появление символа на хосте по Bluetooth.
3. Не найдена команда "войти в pairing" (комбинация Fn2+ESC на стоке не передаёт отдельного HID-кода — возможно, комбинация обрабатывается BT-модулем автономно по обычным скан-кодам, не через отдельную MCU-команду). Не блокирует базовую функциональность.
4. Расширить документацию в `Redragon_K530_Keyboard/` — перенести полные снапшоты исследования (адреса регистров, дизассемблированные функции целиком) для будущих исследователей.

## АПДЕЙТ
### Подтверждённый протокол

- Интерфейс — **SPI** (SN32 = SPI0 **slave**, BT-модуль = **master**). Линии: P0.2=MISO0, P0.3=MOSI0, P0.4=SCK0, P0.5=SEL0/SS (подтверждено дважды: дизассемблированием и архивными PR qmk/qmk_firmware #20838/#20839).
- Регистры SPI0 — база `0x4001C000` (CTRL0, CTRL1, CLKDIV, STAT, IE, RIS/IC на `+0x18`, DATA на `+0x1C`), подтверждено официальным SVD (SN32F240B) и дизассемблером.
- Вектор прерывания SPI0: адрес `0x58` в таблице векторов = IRQ6 (`SN32_SPI0_HANDLER = Vector58`, `SN32_SPI0_NUMBER = SPI0_IRQn` в `sn32_registry.h`).
- **Формат исходящего (TX) кадра — 39 байт** (`0x27`), а НЕ 21: 38 байт данных + 1 байт чек-суммы в `[38]` (сумма байт `[0..37]` по модулю 256). Ранняя оценка «21 байт» оказалась ошибкой (см. тупиковые гипотезы) — рабочая печать по BT получается только на 39-байтном кадре.
  - `[0]` — команда (`0xA1` = 6-key HID-отчёт);
  - `[1]` — «канал»/mode (P1.14, на имя draconic-N НЕ влияет);
  - `[2]` — длина полезной нагрузки;
  - далее payload; `[38]` — чек-сумма.
- **Входящий (RX) статус-кадр от модуля — переменной длины**, завершается байтом бегущей чек-суммы (rolling checksum). Подтверждено вручную на реальном трафике: `A7 00 00 00 03 FF 00 64 … 0x0D`, где `0x0D` совпадает с бегущей суммой предыдущих байт. Именно поэтому RX нельзя резать жёсткой 21/39-байтной рамкой — только по сходящейся контрольной сумме скользящего окна.
- Диспетчер команд (стоковая прошивка, диапазон `0xA1–0xA9`):
  - `0xA1` — 6-key HID-отчёт (нажатия клавиш);
  - `0xA2` — **TX-poll: мастер запрашивает наш кадр**; этим байтом НАЧИНАЕТСЯ каждая транзакция на шине (ключ к синхронизации, см. ниже);
  - `0xA5` — управление линком (реклама/реконнект): `TX[3]` = индекс хоста, `TX[7]` = 0x02 реклама / 0x01 стоп-реконнект;
  - `0xA6` — **переключение активного хоста** draconic-1/2/3: `TX[4]` = индекс хоста (0/1/2);
  - `0xA7` — это **статус-кадр ОТ модуля** (не команда MCU!): `byte[4]` = состояние линка (0x02 = реклама, 0x03 = подключён). Прежнее утверждение «0xA7 = переключение хоста/профиля» — **ошибка**, переключение хоста делает `0xA6`.
- Физические тумблеры: **BT on/off** — GPIO1 бит 13 (P1.13), подтверждено измерением мультиметром (0 = ON, HIGH = OFF). **Выбор хоста 1/2/3** — GPIO0.6 + GPIO0.7, слайдер с общим контактом: в позициях 1/3 один из пинов замкнут на GND/питание, в средней позиции оба пина замкнуты друг на друга (floating). Прошивка кратковременно переключает P0.7 в режим выхода и смотрит реакцию P0.6, чтобы различить все 3 положения.

### Что дало результат (работает)

- **Печать по Bluetooth заработала** после того, как ISR SPI0 стал **самосинхронизироваться по байту `0xA2`**: на каждом `0xA2` (начало транзакции) сбрасываем индекс выдвижения TX-кадра в 0 и начинаем слать кадр с нулевого байта. Жёсткий счётчик «ровно 21 байт» дрейфовал → мастер читал мусор → клавиатура «висла». Самосинхронизация по `0xA2` восстанавливает выравнивание даже при потерянных байтах.
- **Никаких `dprintf`/печати внутри ISR.** Печать в прерывании на скорости побайтового SPI съедает время обработчика → теряются байты → рассинхрон → залипание набора. Все логи вынесены в `bluetooth_task()` по флагу `frame_ready`.
- **RX разбирается по бегущей чек-сумме** скользящего окна (буфер до 64 байт), а не по фиксированной рамке — устойчиво к «холостым» нулевым клокам между сообщениями.
- На границе принятого кадра — `disable() + reinit()` SPI0, как в стоке.
- **Кадр 39 байт** (не 21). С 21-байтным кадром печать не работает.
- Чтение тумблеров (BT on/off по P1.13; слот хоста 1/2/3 по P0.6/P0.7 tri-state) — стабильно детектируется, включая среднее положение.

### Известные тупиковые гипотезы (не тратьте время на них снова)

1. **SELDIS (Auto-SEL, бит 18 CTRL0)** — рассматривался как способ аппаратно привязать начало SPI-транзакции к линии SEL0/CS. Оказался нерелевантным: этот бит описывает поведение периферии в роли SPI **master**, а наш чип работает в **slave**-режиме, где линия CS — вход, управляемый внешним мастером. Бит уже правильно выставлен (Auto-SEL EN) во всех тестах, дрейф синхронизации сохранялся независимо от этого бита.
2. **RXTOIF (RX time-out interrupt, RIS/IE/IC бит 1, порог 32×SPIn_PCLK по даташиту Sonix)** — рассматривался как альтернативный триггер границы кадра вместо программного счётчика байт. Эмпирически исключён: на реальном железе флаг срабатывает практически непрерывно и всегда «посреди» уже идущего приёма (порог оказался слишком коротким — вероятно это 32×HCLK напрямую, ≈0.67 мкс при 48МГц, а не 32×делённой через CLKDIV частоты). Использовать этот флаг как границу кадра нельзя.
3. **CPHA/CPOL (полярность/фаза SPI)** — проверено числами из `SPI.h`: `SPI_CPHA_FALLING_EDGE=0`, `SPI_CPOL_SCK_IDLE_LOW=0`, `SPI_MLSB_MSB=0`. Безусловная запись `CTRL1=0` в стоковой прошивке точно совпадает с этими «стандартными» значениями — это не источник проблемы.
4. **Задержка `disable()+reinit()` между кадрами** — измерена через `SysTick->VAL` на реальном железе: **0 тиков**, то есть не является узким местом.
5. **Длина кадра 21 байт** — **ошибка**. Стоковый TX-кадр = **39 байт** (чек-сумма в `[38]`). Сборка с 21-байтным кадром + переписанным на «sync_ring» ISR **полностью ломала печать** по BT.
6. **Инъекция командных кадров `0xA5`/`0xA6` для смены имени draconic-N** — **не работает**. Множество тестов (21-байтный A5, 39-байтный A5, 39-байтный A6): рекламируемое имя не менялось ни в одном положении тумблера. Имя и бонд полностью управляются самим PixArt-модулем, а не SN32.
7. **Имена/профили НЕ лежат в SN32.** В дампе стоковой прошивки строк «draconic» нет вообще; flash-профили `0xA080` (3×42 Б) и per-slot скрипты `0xA740` (3×0x17A) **байт-в-байт идентичны и пустые** для всех трёх слотов. Вывод: сопоставление «индекс хоста → имя + бонд» живёт внутри BT-модуля.
8. **OFF — это НЕ разрыв соединения по SPI.** Отдельной команды «disconnect»/«stop» не найдено; при выключенном тумблере модуль автономно продолжает рекламу/реконнект, а простое отключение SPI0 рекламу не гасит.
9. **Гипотеза «модуль читает селектор хоста по отдельному пину»** — снята: между SN32 и модулем только 5 SPI-линий.

### Решённый вопрос: синхронизация RX/TX

Ранее это был главный открытый вопрос (дрейф позиции кадра из-за «холостых» клоков между сообщениями). **Решено:** синхронизация не по жёсткому счётчику и не по чистому rolling-checksum-окну, а по **самосбросу TX-индекса на каждом `0xA2`** (начало транзакции) + разбор RX по бегущей чек-сумме + отсутствие печати в ISR. С этим набором печать по Bluetooth работает стабильно.

### Текущий открытый вопрос: смена имени draconic-N по слоту

Переключение рекламируемого имени по тумблеру 1/2/3 через командные кадры **не достигается** (см. тупики 6–8): имя/бонд автономно держит BT-модуль. Оставшиеся реалистичные направления:

- реверс **загрузочного handshake** стока (что именно SN32 шлёт модулю в первые миллисекунды после включения — возможно, там инициализируется таблица хостов);
- либо принять поведение «одно имя» и оставить переключение слотов только на уровне индикации (см. ниже).

## АПДЕЙТ 2 — тумблер 1/2/3 работает, холодный старт как в стоке, заглушки LED

> Этот раздел **отменяет пессимизм** прежних выводов: тупики 6–8 и «Текущий открытый вопрос: смена имени draconic-N по слоту» устарели. Переключение имени по тумблеру **достигнуто**. Ниже — что сделано и как реализовано, без повторов написанного выше.

### Смена имени draconic-N по тумблеру 1/2/3 — РЕШЕНО (работает)

Раньше считалось, что имя автономно держит модуль и командами его не переключить. На практике оказалось, что переключение **работает**, если слать `0xA6` строго как сток. Что сделано:

- Флаг `k530_bt_host_switch_enabled` переведён в `true` (раньше был выключен «до лучших времён»).
- На **живое** изменение положения селектора шлётся **ровно один** кадр `0xA6` c `TX[4]` = индекс слота (0/1/2 → draconic-1/2/3). Это зеркалит стоковую связку «детектор `0x56D6` → сериализатор `0x02AC`».
- **Settle-debounce селектора** (`K530_HOST_SLOT_SETTLE_POLLS`): счётчик сбрасывается при каждом изменении сырого положения, поэтому ручная прокрутка 1→2→3 **не фиксирует** промежуточный слот 2 — команда уходит один раз, по финальному устоявшемуся положению. Раньше счётчик копил через всю прокрутку и коммитил случайный слот → имя менялось хаотично.
- Перед кадром `0xA6` — **праймер-строб на P0.1** (1 мс HIGH / 100 мс LOW). Это ровно то кратковременное мигание подсветки, которое видно на стоке при щелчке 1/2/3 (стоковый праймер `0x043C`).
- Тайминги вокруг отправки: `wait_ms(20)` до и `wait_ms(40)` после (как в стоке).
- Глушение по ON/OFF (`0xA5`, `C2`/`BB`) работает и не мешает переключению слота.

### Точная механика стока при смене хоста (подтверждено дизассемблером)

- Детектор селектора `0x56D6` при устоявшейся смене вызывает хвост `0x5700–0x5726`: flash-read `0x913C` → `wait_ms(20)` → отправка `0x02AC` → `wait_ms(40)` → `[0xBF]=0` → `[0xBD]=idx`.
- Сериализатор `0x02AC` строит `A6`-кадр по одноразовому флагу (gate bit5 в `[0x20000008]`), кладёт `out[3]=[0xBE]`, `out[4]=[0x110+0x15]`.
- **Сток шлёт РОВНО ОДИН `0xA6`**: нет ретраев, нет проверки по `0xA7`, нет предварительного `0xA5`-disconnect. Сразу после отправки `[0x200000BD]` (last-applied) обновляется на новый индекс, поэтому повторно тот же слот сток не досылает.

### Остаточный нюанс — он ЕСТЬ и в стоке (не регресс, не трогаем)

Переключение из **уже подключённого** состояния (link = `0x03`), например 2→3 при активном коннекте с телефоном, **изредка** не проходит с первого щелчка: «голый» `0xA6` из подключённого состояния честно исполняется примерно 5 раз из 6. Это латентная особенность **самого стока** (там тоже нет ни ретрая, ни verify). Поскольку задача была «сделать как в стоке», логику намеренно **не усложняли**. Если позже захочется 100% надёжности — единственный кандидат-обход: перед `0xA6` слать `0xA5`-disconnect, когда link==`0x03`. Это уже отход от стока.

### Холодный старт — теперь строго как в стоке

Выяснено по загрузочному пути стока (`0x0B80–0x0BB0`):

- При холодном старте сток **НЕ пишет** положение тумблера во флеш. Он **читает** статический индекс из флеша `0xA080` (`BL 0x913C` — только чтение, ни program, ни erase во всём boot-пути), шлёт один `0xA6` с этим индексом и отдаёт остальное модулю.
- Физический селектор на загрузке сток **не сэмплирует** для выбора хоста.
- Персистентная память «последний хост» живёт **в NV-памяти самого BT-модуля** (PixArt), а не во флеше SN32. Поэтому клавиатура на включении поднимается на том хосте, что запомнил модуль.

Правка в нашем коде (`k530_poll_host_slot`): подавлён **самый первый** `0xA6` при переходе `UNKNOWN → слот` сразу после загрузки — теперь cold boot не сэмплирует тумблер и не форсирует хост, а переключение срабатывает только на **живой** щелчок. Это делает поведение идентичным стоку.

**Важное следствие (как и в стоке):** если сменить тумблер на **обесточенной** клавиатуре, это положение нигде не фиксируется — при следующем включении клавиатура поднимется на хосте, который помнит модуль (последний активный при питании), а не на новом положении тумблера. Это штатное поведение стока.

### Заглушки под два светодиода у тумблера (добавлены в `bluetooth.c`)

В `bluetooth.c` добавлены две пустые функции-заглушки и точки их вызова:

- `k530_led_host_indicator_set(k530_host_slot_t slot)` — индикатор активного хоста (какой draconic 1/2/3 рекламируется). Вызывается сразу после отправки `0xA6` и периодически в `bluetooth_task()`.
- `k530_led_battery_indicator_set(uint8_t battery_raw)` — индикатор заряда батареи. Вызывается периодически в `bluetooth_task()` (значение берётся из A7-статус-кадра).

Тела **намеренно пустые** — реальные GPIO-пины и цвета ещё предстоит выяснить по стоку. **Уточнение к прежнему README:** конкретная раскладка цветов (1=красный/2=зелёный/3=синий, батарея зелёный→красный) в стоке **не подтверждена** — это была догадка. Достоверно известно только: **полный заряд = зелёный**. Остальные цвета host-LED по слотам и пороги/цвета batt-LED нужно реверсить. Отправная точка в дизассемблере: запись LED около `0x5728` по адресу `0x40044000` бит 7 (там же рядом обработчик смены хоста `0x56D6` и разбор `0xA7`).

Тумблер ON\OFF тоже корректно работает

## АПДЕЙТ 3 — сброс сопряжения найден, взаимоблокировка USB/BT, рабочие индикаторы у тумблера

> Этот раздел **отменяет пессимизм шапки** («Bluetooth в процессе»): основная BT-функциональность собрана и подтверждена на реальном железе. Проект фактически готов — осталась **одна калибровка**: пороги индикатора батареи (см. конец раздела). Ничего из написанного выше не удалено; здесь — только новое.

### 🎯 Сброс сопряжения / re-pair — РЕШЕНО

Давний открытый вопрос («войти в pairing / забыть бонд», см. пункт 4 в «Как продолжить работу») **закрыт** полным реверсом жеста. Прежний вывод «Fn2+ESC не передаёт отдельного кода» оказался неверным — код есть, просто он неочевидный.

- **Жест:** `Fn2 + ESC`, удержание **3 секунды** (как в стоке).
- **Что уходит модулю:** команда `0xA6`, **но с `byte[3] = 0x01`**. Это тот же опкод, что и переключение хоста, — но обычное переключение шлёт `byte[3] = 0x02`. Значение `0x01` в этом байте пишется во всей стоковой прошивке **ровно в одном месте** — на пути 3-секундного удержания Fn2+ESC (адрес `0x0B7E`). Именно поэтому все прежние тесты «отправить `0xA6`» бонд не чистили: это всегда был вариант `0x02` (смена хоста).
- **Полный кадр:** `A6 02 05 01 <hostIdx> 00 … 00 <cksum>`, где `hostIdx` — текущий слот (0-based: draconic-1 → 0 … draconic-3 → 2).
- **Подтверждено на железе:** команда **универсальна** — сбрасывает бонд на любом из трёх слотов (маркер `0x01` единый; `byte[4]` просто следует за текущим хостом). После сброса телефон/ПК создаёт **новую** пару без ошибки «устройство пропадает из списка».

**Механика в стоке (дизассемблер):** по фронту нажатия обработчик действия `0x2C` (запись в таблице Fn2-комбо `0xCD50`) кадр НЕ шлёт, а взводит бит6 в `[0x20000008]` и обнуляет счётчик `[0x200000B7]`. Периодический планировщик тикает счётчик, и по достижении `0x37` (=55, это и есть ~3 сек) собирает и отправляет кадр `0xA6/0x01` через сериализатор `0x02AC`.

### 🔒 Взаимоблокировка USB / Bluetooth (как в стоке)

- Тумблер BT в **ON** → проводная клавиатура **немеет**: базовые клавиши (буквы/цифры/модификаторы, keycode ≤ `0xFF`) уходят **только по Bluetooth**, USB-отчёт подавляется.
- Тумблер в **OFF** → провод снова активен.
- Служебные и составные коды (переключение слоёв, `RESET`, `RGB_TOG`, кастомные > `0xFF`) проходят **всегда**, чтобы не ломать раскладку и служебные клавиши.

### 💡 Два индикатора у тумблера — реализованы (заглушки из АПДЕЙТа 2 заменены рабочим кодом)

Найдены реальные индексы светодиодов в матрице (позиции из рабочего конфига Steryy/k530, row4 col3/col4): **LED 62 = состояние линка**, **LED 61 = батарея**. Красятся **последними** в `rgb_matrix_indicators_advanced_user()` — поверх эффектов и OpenRGB. Для этих двух индексов direct-эффект OpenRGB **пропускается** (чтобы асинхронный PWM-скан не ловил промежуточный кадр → нет мерцания).

#### Таблица индикации состояния линка — **LED справа у тумблера (индекс 62)**

Значение берётся из статус-кадра модуля `0xA7`, байт `[4]`:

| Состояние BT-модуля | Индикатор |
|---|---|
| Подключён к устройству (`0x03`) | 🟢 **зелёный**, ровно горит |
| Есть бонд, но устройства рядом нет (`0x01`) | 🟢 **зелёный**, мигает |
| Реклама / доступна для подключения (`0x02`) | 🔵 **синий**, мигает |
| Простой / нет активного бонда (`0x00`) | 🔴 **красный**, мигает |
| Отправлена команда сброса (Fn2+ESC 3 сек) | 🔴 **красный**, мигает ~6 сек — подтверждение, что команда ушла |
| Тумблер BT в OFF | ⚫ потушен |

#### Таблица индикации батареи — **LED слева у тумблера (индекс 61)**

Значение берётся из `0xA7`, байт `[7]`. Пороги **предварительные** (см. «Осталось сделать»):

| Заряд | Индикатор |
|---|---|
| > 60 % | 🟢 **зелёный** |
| 25–60 % | 🟡 **жёлтый** |
| < 25 % | 🔴 **красный** |
| Тумблер BT в OFF | ⚫ потушен |

#### Индикация раскладки и клавиш (подсветка, не у тумблера)

Для полноты — что означают цвета в самой раскладке:

| Что подсвечено | Цвет |
|---|---|
| Активен слой Magic Fn (удержание CapsLock) | 🟠 оранжевый |
| Активен слой Fn2 | 🔴 красный |
| Активен слой Fn1 | 🟢 зелёный |
| Клавиша `RESET` (сброс в bootloader) | 🔴 красный (всегда) |
| Клавиша `RGB_TOG` (MR / Backspace) | 🟣 фиолетовый (всегда) |
| Слот макроса записан / пуст (при удержании Magic Fn или Fn2+выбор) | 🟢 зелёный / 🔴 красный |
| Реактивное нажатие любой клавиши | ⚪ белый → плавное затухание в тёмно-серый фон (800 мс) |

### ⏳ Осталось сделать (единственный пункт)

- **Калибровка индикатора батареи.** Все логи снимались при подключённой зарядке (`byte[7] = 0x64` = 100 %), поэтому точная кодировка поля заряда (реальный процент 0–100 / сырой ADC / уровни) и наличие отдельного бита «на зарядке» ещё уточняются реверсом разбора `0xA7`-статуса в стоке. Пороги/цвета в таблице выше — рабочая заглушка, будут уточнены после калибровки.
