# K530 QMK + Bluetooth (reverse-engineered) + OpenRGB

Кастомная прошивка QMK для клавиатуры **Redragon K530 Draconic** (главный чип Sonix SN32F248B + Bluetooth-модуль PixArt PAR2801QN-GHVC), собранная на основе форка [SonixQMK/qmk_firmware](https://github.com/SonixQMK/qmk_firmware), ветка `sn32_master_openrgb`.

> **Статус: экспериментальный проект, работа не закончена.** Прошивайте на свой риск. Обязательно сохраните бэкап стоковой прошивки и заранее убедитесь, что знаете способ восстановления (см. раздел «Bootloader / восстановление» ниже), прежде чем экспериментировать.

Этот README написан подробно специально для того, чтобы следующий человек (или ИИ-модель), который продолжит проект, не повторял уже пройденные тупиковые пути. Весь путь разработки велся в переписке с ИИ-ассистентами (реверс-инжиниринг прошивки в Ghidra, сборка QMK, отладка на реальном железе) — здесь собран итог.

## Цели проекта

1. **Полноценный per-key RGB через OpenRGB / Skydimo** (direct mode) — вместо ограниченного стокового RGB (только переключение пресетов).
2. **Кастомная раскладка**: слои Fn / Fn2, Magic Fn (удержание CapsLock), запись/воспроизведение макросов (6 слотов) с LED-индикацией, реактивная подсветка при нажатии клавиш.
3. **Восстановленная поддержка Bluetooth** — чтобы клавиатура сохраняла BLE-соединение при полностью кастомной QMK-прошивке (все существующие альтернативные community-прошивки полностью убирают BT).

## Железо

- Главный чип (MCU): **Sonix SN32F248B**, маркировка на плате `VS11K09A-1` (бренд eVision), ядро ARM Cortex-M0.
- Bluetooth-модуль: **PixArt PAR2801QN-GHVC** (он же PAJ2801UA-40, FCC ID 2AIPB-PAJ2801UA-40), BLE.
- Связь MCU↔BT — **SPI**, модуль работает как **SPI master**, главный чип — как **SPI slave**.
- Линии SPI (со стороны MCU): **P0.2=MISO0, P0.3=MOSI0, P0.4=SCK0, P0.5=SEL0/SS**. Подтверждено независимо: PR qmk/qmk_firmware #20838/#20839, распиновка платы (A1-A5), и дизассемблированием стоковой прошивки.
- Периферия SPI0 на уровне регистров: база `0x4001C000` (`CTRL0`, `CTRL1`, `CLKDIV`, `STAT`, `IE`, `RIS`, `IC` на `+0x18`, `DATA` на `+0x1C`). Подтверждено официальным SVD (`SN32F240B.svd`) и дизассемблером.
- Вектор прерывания SPI0: адрес `0x58` в таблице векторов = IRQ6. В ChibiOS-Contrq: `SN32_SPI0_HANDLER = Vector58`, `SN32_SPI0_NUMBER = SPI0_IRQn` (файл `sn32_registry.h`).
- **2 физических тумблера:**
  - **BT on/off** — читается на **GPIO1, бит 13** (P1.13). Подтверждено измерением мультиметром: тумблер ON → 0В (замкнут на GND), OFF → подтяжка к высокому уровню.
  - **Выбор хоста 1/2/3** — читается через **GPIO0.6 (P0.6) и GPIO0.7 (P0.7)**. Механика: слайдер с одним общим контактом — в позициях 1/3 один из пинов явно замкнут на GND/питание, в средней позиции (2) оба пина замкнуты друг на друга и «висят» (floating). Прошивка активно переключает P0.7 между режимом входа/выхода и смотрит на реакцию P0.6, чтобы различить все 3 положения.
- Boot-pin (вход в аппаратный ISP bootloader): физический вывод №3 чипа (`BOOT/PWM10B/P2.2/AIN2` по даташиту) — замкнуть на GND при подаче питания. Работает независимо от состояния прошивки, это самый надёжный способ восстановления.
- Jumploader **не требуется** для этого семейства чипа (SN32F248B) — по официальной документации SonixQMK jumploader нужен только для SN32F26x. Прошивайте с **offset 0x00**.

## Протокол Bluetooth — что установлено реверс-инжинирингом

Подробные заметки (дизассемблированные функции, адреса, найденные строки) — в файле [`docs/bluetooth-protocol.md`](docs/bluetooth-protocol.md) (перенести туда полные снапшоты исследования). Кратко:

### Формат кадра
- Кадр = **21 байт**: 20 байт данных + 1 байт чек-суммы (простая арифметическая сумма первых 20 байт по модулю 256).
- Подтверждено дважды независимо — и со стороны TX (функция сборки исходящего отчёта), и со стороны RX (обработчик прерывания SPI0 в дампе стоковой прошивки).
- Найденный командный байт стоковой прошивки для смены хоста: **`0xA7`** (близко к `0xA6` из референсного протокола похожих чипов CKBT51, но не идентично — протокол архитектурно похож, но кастомизирован под EVision/K530).
- Диспетчер исходящих отчётов (стоковая прошивка): команды `0xA1` (6-key HID), `0xA2` (запрос TX-буфера), `0xA3` (медиа), и другие в диапазоне `0xA1-0xA9`.

### Обработчик прерывания SPI0 (реконструирован дизассемблированием, стоковая прошивка)
Машина состояний: 1 байт = команда, следующие 20 байт — тело кадра, последний байт — чек-сумма. Ответ формируется динамически в зависимости от команды (в т.ч. эхо предыдущих байт, либо байт из TX-буфера).

### Известные тупиковые гипотезы (не тратьте время на них снова)

1. **SELDIS (CTRL0 бит 18, Auto-SEL flow control)** — рассматривался как способ аппаратно привязать начало SPI-транзакции к линии SEL0/CS. **Оказался нерелевантным**: этот бит описывает поведение периферии в роли SPI **master**, а наш чип работает в **slave**-режиме, где линия CS — вход, управляемый внешним мастером, и SELDIS тут не при чём. Бит уже правильно выставлен (Auto-SEL EN) во всех тестах, дрейф синхронизации сохранялся независимо от этого бита.
2. **RXTOIF (RX time-out interrupt, RIS/IE/IC бит 1, порог 32×SPIn_PCLK по даташиту Sonix)** — рассматривался как альтернативный триггер границы кадра вместо программного счётчика байт. **Эмпирически исключён**: на реальном железе флаг срабатывает практически непрерывно и всегда «посреди» уже идущего приёма (порог оказался слишком коротким — вероятно это 32×HCLK напрямую, ≈0.67 мкс при 48МГц, а не 32×делённой через CLKDIV частоты). Использовать этот флаг как границу кадра нельзя.
3. **CPHA/CPOL (полярность/фаза SPI)** — проверено числами из `SPI.h`: `SPI_CPHA_FALLING_EDGE=0`, `SPI_CPOL_SCK_IDLE_LOW=0`, `SPI_MLSB_MSB=0`. Безусловная запись `CTRL1=0` в стоковой прошивке точно совпадает с этими «стандартными» значениями — это не источник проблемы.
4. **Задержка `disable()+reinit()` между кадрами** — измерена через `SysTick->VAL` на реальном железе: **0 тиков**, то есть не является узким местом.

### Открытый вопрос (на момент этого README)
Анализ сырого потока байт (без интерпретации через 21-байтную рамку) на реальном железе показал воспроизводимый паттерн: `A7 00 00 00 03 FF 00 64` + ~12-17 «холостых» нулевых байт + `0D` + затем одиночный байт `A2` (запрос) — то есть 21-байтный кадр подтверждён чек-суммой (`A7+03+FF+64 mod 256 = 0x0D`, сходится), но между логическими сообщениями от BT-модуля идут «холостые» клоки/байты, которые текущая реализация (программный счётчик `!k530_receiving`, сбрасываемый только после ровно 21 принятого байта) не умеет корректно пропускать — отсюда дрейф позиции кадра при разборе вручную. **Наиболее многообещающее направление на данный момент:** синхронизация через скользящее окно на 21 байт с проверкой чек-суммы на каждый новый принятый байт (rolling checksum), вместо жёсткой границы «раз в 21 байт», — считать кадр найденным только когда контрольная сумма скользящего окна сошлась. Это не зависит от количества и происхождения холостых байт между сообщениями.

## Физические тумблеры — как читаются в прошивке

```c
// GPIO1 бит 13 — BT on/off
// 0 = ВКЛЮЧЕН (тумблер замкнут на GND)
// 1 = ВЫКЛЮЧЕН

// GPIO0 бит 6 (P0.6) и бит 7 (P0.7) — слот хоста
// Позиция 1: P0.6=HIGH, P0.7 floating
// Позиция 2 (средняя): P0.6 и P0.7 замкнуты друг на друга
// Позиция 3: P0.6=GND, P0.7 floating
// Прошивка кратковременно настраивает P0.7 как выход и проверяет реакцию P0.6
```

## Сборка прошивки

```bash
# через QMK CLI (нужен Python 3.11, см. примечание про баг ast.Num на 3.12+)
qmk setup SonixQMK/qmk_firmware -b sn32_master_openrgb   # либо клонировать этот репозиторий напрямую
# скопировать содержимое keyboards/redragon/k530 из этого репозитория поверх
qmk compile -kb redragon/k530 -km default
```

**Известный баг окружения:** QMK CLI на Python 3.12+ падает с `AttributeError: module 'ast' has no attribute 'Num'` (устаревший API, убран в новых версиях Python). Решение — отдельное виртуальное окружение на Python 3.11:
```bash
sudo add-apt-repository ppa:deadsnakes/ppa -y && sudo apt update
sudo apt install python3.11 python3.11-venv -y
python3.11 -m venv ~/qmk-env && source ~/qmk-env/bin/activate
pip install qmk
```

**Если включена консоль для отладки (`CONSOLE_ENABLE=yes`)** — учитывайте лимит USB endpoint'ов чипа: одновременно Console + NKRO + Extra Keys + OpenRGB (Raw HID) может не поместиться («There are not enough available endpoints...»). Временно отключайте NKRO/Extra Keys на время отладки Bluetooth, возвращайте после.

## Прошивка / Bootloader / восстановление

- **Обычная прошивка:** через [Sonix Flasher](https://github.com/SonixQMK/sonix-flasher) или официальный EVision-инструмент, **offset 0x00**.
- **Вход в bootloader программно:** кейкод `RESET` (или `QK_BOOT` в новых версиях QMK) в раскладке — например, комбинация Fn+правый Ctrl в этом keymap.
- **Аппаратный вход в bootloader (работает всегда, независимо от состояния прошивки):** разобрать клавиатуру, найти вывод №3 чипа (маленькая метка-точка на корпусе чипа — от неё отсчитать против часовой стрелки: 1, 2, 3), замкнуть его на GND (например, экран USB-разъёма) **в момент подачи питания** (подключения USB-кабеля). Подождать ~30-60 сек после отключения питания перед этим, чтобы конденсаторы разрядились.
- **Sonix Flasher / Jumploader** — для этого чипа (SN32F248B) НЕ нужен, несмотря на то что интерфейс Sonix Flasher может предлагать его установить. Установка Jumploader меняет требуемый offset на 0x200 и требует правки линкер-скрипта — усложняет процесс без явной необходимости для этого конкретного чипа.

## OpenRGB / Skydimo — настройка

1. Прошейте сборку с `OPENRGB_ENABLE = yes` (уже включено в этом репозитории).
2. **OpenRGB**: устройство не появляется автоматически — нужно вручную зарегистрировать через **Settings → OpenRGB QMK Protocol → Add** (VID `0x0C45`, PID `0x5004`), нажать **Save**, затем **полностью перезапустить OpenRGB** (не просто Rescan — детекторы регистрируются один раз при старте программы), и только потом Rescan.
3. **Skydimo**: используйте кастомный Lua-плагин из папки `/skydimo-plugin` этого репозитория — кладётся в `%APPDATA%\com.skydimo.desktop\plugins\dev\`. Реализует протокол QMK OpenRGB (те же команды, что и `quantum/openrgb.c`) через `device:write()`/`device:read()`. Interface number для HID-правила в `manifest.json` — **1** (подтверждено через USB Tree View: Interface 1, Usage Page `0xFF60`, Usage `0x61`).
4. Если белый цвет (255,255,255) выглядит розовым на вашей подсветке — это дисбаланс каналов светодиодов, а не баг софта. В этом репозитории используется скорректированное значение (примерно R150/G255/B100) вместо чистого белого в местах, где это важно (LED-индикация в keymap.c).

## Известные тупики при сборке прошивки (чтобы не наступать на те же грабли)

- **Version drift между ветками SonixQMK.** Ветки `sn32_develop`, `sn32_master`, `sn32_master_openrgb` и другие расходятся по версиям кейкодов (`KC_MS_UP` → `MS_UP`, `RGB_HUI` → `RM_HUEU`, `RESET` → `QK_BOOT`/обратно и т.д.), формату `info.json`/`keyboard.json`, именам RGB-драйверов (`SN32F24xB` vs `sn32f2xx`). Если берёте конфиг клавиатуры из стороннего репозитория — проверяйте, на какой именно версии/дате он собирался (`git log --before=... -1` в нужной ветке), и либо переключайтесь на тот же коммит, либо адаптируйте вручную.
- **`redragon/k530` отсутствует в ветке `sn32_develop`** — она есть только в `sn32_master`/`sn32_master_openrgb`/старых снэпшотах. Не тратьте время на поиск в `sn32_develop`.
- **VIA + OpenRGB одновременно не работают** в этой версии — `common_features.mk` явно выдаёт ошибку компиляции при попытке включить оба флага разом (общий RAW HID endpoint, конфликт протоколов).
- **ColorHoster** (github.com/Azarattum/ColorHoster) — альтернативный путь для совместного использования VIA+RGB, работает поверх VIA-протокола, а не через `OPENRGB_ENABLE`. Не проверялось на этом проекте, но выглядит перспективным направлением для будущего исследования, если понадобится VIA.

## Как продолжить работу

1. **Главный приоритет** — решить синхронизацию границы RX-кадра в Bluetooth-протоколе (см. раздел выше). План: rolling checksum по скользящему 21-байтному окну вместо жёсткого счётчика.
2. После стабильного приёма — протестировать полный цикл: нажатие клавиши → передача по SPI → приём BT-модулем → появление символа на хосте по Bluetooth.
3. Не найдена команда "войти в pairing" (комбинация Fn2+ESC на стоке не передаёт отдельного HID-кода — возможно, комбинация обрабатывается BT-модулем автономно по обычным скан-кодам, не через отдельную MCU-команду). Не блокирует базовую функциональность.
4. Расширить документацию в `/docs` — перенести полные снапшоты исследования (адреса регистров, дизассемблированные функции целиком) для будущих исследователей.

## Инструменты, использованные в разработке

- **Ghidra** — дизассемблирование стоковой прошивки (ARM Cortex-M0, base address 0x0).
- **SVD-Loader for Ghidra** — автоматическая разметка регистров по официальному SVD-файлу (`SN32F240B.svd` из репозитория IslamAlam/blitzwolf-bw-kb-1, тот же чип).
- **QMK CLI / WSL2 (Ubuntu)** — сборка прошивки.
- **Sonix Flasher** — прошивка через USB.
- **hidapitester** (github.com/todbot/hidapitester) — низкоуровневое тестирование HID-пакетов независимо от OpenRGB/Skydimo, помогло выявить, что прошивка отвечает корректно, а проблема была на стороне детектора клиентского софта.
- **Wireshark + USBPcap** — анализ реального USB-трафика между ПК и клавиатурой.
- **QMK Toolbox / hid_listen** — просмотр консольного вывода (`dprintf`/`uprintf`) с клавиатуры для отладки.
